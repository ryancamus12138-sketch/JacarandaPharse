# 评测

怎么跑、指标怎么算、每次的结果。方案见 [ADR 0023](../adr/0023-evaluation.md)。

## 怎么跑

```bash
uv run jacara eval download                          # 第一次：下载 SROIE 到 datasets/sroie（要联网）
uv run jacara serve --model models/<模型>.gguf       # 另一个终端：启动本地大模型
uv run jacara eval sroie --limit 20                  # 先跑 20 张试试
uv run jacara eval sroie                             # 全部 626 张
```

结果在 `results/eval/<时间>/`：`summary.md`（表格）、`summary.json`（数字）、`fields.jsonl`（每个字段一行，找错例用）。

## 指标

| 指标 | 意思 | 希望 |
| --- | --- | --- |
| 准确率 | 模型的值和标准答案一样 | 高 |
| 宽松准确率 | 文字只差 OCR 错字（相似度 ≥ 90%）也算对；和准确率的差距就是 OCR 错字的影响 | 高 |
| 出处覆盖率 | 在原文里找到出处 | 高 |
| 错值拦截率 | 错的值里，被标黄交给人的比例 | 高 |
| 误报率 | 对的值里，也被标黄的比例 | 低 |
| 放行率 | 没标黄、直接放行的比例 | 高（省人工） |
| 放行准确率 | 直接放行的值里，对的比例 | 越接近 100% 越好 |

## 找错例

```bash
# 没标黄但是错了的（最危险）
grep '"correct": false' results/eval/<时间>/fields.jsonl | grep '"flagged": false'
```

### 2026-11-11 全量基线（626 张）

| 字段 | 准确率 | 出处覆盖率 | 错值拦截率 | 误报率 | 放行准确率 |
| --- | --- | --- | --- | --- | --- |
| 商家 | 65.7% | 99.7% | 5.1% | 5.4% | 65.6% |
| 日期 | 96.8% | 88.7% | 65.0% | 11.1% | 98.7% |
| 总额 | 94.1% | 98.2% | 29.7% | 0.5% | 95.8% |
| 全部 | 85.5% | 95.5% | 12.9% | 5.7% | 86.5% |

结论：日期和总额"没标黄就可以信"基本成立（98.7%、95.8%），**商家还不成立（65.6%）**。215 个错的商家里：

- **约 73 个多抄了东西**：把公司注册号带进来了（`99 SPEED MART S/B (519537-X)`），或者多了分店、业态（`THREE STOOGES BISTRO & CAFE`）。是字段说明没写清楚。
- **约 76 个选了另一个名字**：店名和公司名不一样时（`BAR WANG RICE` 和 `UNIHAKKA INTERNATIONAL SDN BHD`），模型选了店名，SROIE 的答案是开票的公司。要先定"商家"指哪一个。
- **约 51 个是 OCR 认错的字**（`LJAN HING`、`SON BHD`）：原文里就是错的，出处证明不了它对。
- 其余是只抄了一半、或者没抽出来。

日期：55 个抽对了却找不到出处，原文写法还没覆盖全，比如 `5/3/2018`（不补 0）、`28 MAR 18`、`02/JAN/2017`、`25032018`。
总额：24 个错值没拦住，主要是四舍五入前后两个数（72.95 和 72.93）、OCR 丢了小数点（1200 和 12.00）。

改进方向，按价值排序：商家的字段说明（receipt 模板第 2 版）→ 日期写法补全 → 评测加"宽松准确率"区分 OCR 错字和选错 → 总额用小计和四舍五入交叉校验。

### 2026-11-11 基线发现的问题

- **两位年份找不到出处**：3 张收据写 `12-01-19`、`18/03/18`，日期其实抽对了，但对齐只认四位年份，于是被标黄（误报 15%）。已修：对齐加上两位年份的写法。
- **OCR 认错的字，出处也是错的**（011）：OCR 把 HARDWARE 读成 HARDWAKE，模型照抄，原文里"找得到"，所以没被标出。出处只能证明"值来自原文"，证明不了"原文认对了"。以后可以考虑 OCR 置信度低时也标黄。
- **商家选错了**（008）：收据上有两个公司名，模型选了另一个；它也在原文里，所以没被标出。要靠位置提示（商家一般在最上面）或人工确认。
- **总额差 0.01**（008）：112.46 和 112.45，可能是四舍五入调整前后的两个数。常用 4 个字段里没有"调整"，规则查不出来。

| 字段 | 准确率 | 宽松准确率 | 出处覆盖率 | 错值拦截率 | 误报率 | 放行准确率 |
| --- | --- | --- | --- | --- | --- | --- |
| 商家 | 79.2%（基线 65.7%） | 86.1% | 99.7% | 8.9% | 5.5% | 79.8%（基线 65.6%） |
| 日期 | 96.8% | 96.8% | 90.6%（基线 88.7%） | 78.9% | 9.0% | 99.2% |
| 总额 | 95.8% | 95.8% | 98.8% | 32.0% | 0.7% | 97.1% |
| 全部 | 90.6%（基线 85.5%） | 92.9% | 96.4% | 20.2% | 5.1% | 92.0%（基线 86.5%） |

结论：

- 商家涨了 13.5 个百分点：定义成"开票的公司"、不带注册号之后，选错名字和多抄注册号的大部分没了。
  宽松准确率 86.1%，说明剩下的错里约 7 个百分点是 OCR 错字，要靠人工确认。
- 加了商品明细后，总额的误报率没有变高（0.5% → 0.7%）：商品合计规则只标商品金额、不标总额，这个设计有效。
- **29 张失败**，全是"模型的回答不是合格的 JSON"：商品多的收据，回答超过了 `max_tokens = 1024`，JSON 写到一半被截断。
  先把上限调到 4096，并在被截断时直接报"回答太长被截断"。这 29 张不在上面的指标里，下次全量评测要确认它们恢复。
  之后一张商品很多的真实收据在 4096 也被截断，于是提示词改为 extract-v4：表格每行只写一次行号、格子直接写值；
  并且不再限制回答长度，上下文调到 32768（表格必须完整，ADR 0026）。单个字段的写法没变，
  上面的指标仍可作为参考，但要用 v4 重跑一次全量。
- 用时 8281 秒（平均每张约 13 秒），比只有单个字段时慢，主要是要写出商品表。
- 之后"视觉行"合并改成按文字倾斜方向比较（歪着拍的照片会被粘成几大行）。SROIE 前 40 张里有 20 张的分行变了，
  抽查都是变好（原来粘在一起的两列、两行被分开）。抽取用的 OCR 文字变了，必须重跑全量评测。
