# 0001 用 ADR 记录架构决策

- 状态：已采纳
- 日期：2026-11-01

## 背景

项目会做很多技术选择（用什么数据库、什么模型、怎么分层）。半年后回头看，最容易忘的不是"选了什么"，
而是"为什么这么选、当时放弃了什么"。AI 助手每次也需要知道这些前提，否则会建议推翻已经定好的东西。

## 决策

每个重要的技术选择写一条 ADR（Architecture Decision Record），放在 `docs/adr/`，
文件名 `NNNN-简短标题.md`，编号递增、不复用。

每条 ADR 包含四部分：

1. **背景**：遇到了什么问题，有哪些约束
2. **决策**：选了什么
3. **放弃的方案**：考虑过什么，为什么没选
4. **后果**：带来的好处、代价，以及以后什么情况下需要重新评估

ADR 写好后不改内容。决策变了就写一条新的，把旧的状态改为"被 NNNN 取代"。

## 后果

- 好处：决策有据可查，新人和 AI 都能快速理解项目为什么是现在这样。
- 代价：每个重要决策多花 10 分钟写文档。
- "重要"的判断标准：改起来要动很多代码，或者影响授权、离线、数据安全。
