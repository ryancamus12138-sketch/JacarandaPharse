# 0005 证据对齐：给每个值在原文里找出处

- 状态：已采纳
- 日期：2026-11-03

## 背景

产品承诺"每个值都能回到原文找到出处，找不到的标红"。大模型可能编值、改字或说错位置，
OCR 也会读错（高置信度地读错，例如 1.00 读成 100）。不能只相信模型的回答。

## 决策

**1. 按视觉行合并 OCR 结果（`plugins/ocr/layout.py`）。** 文字块上下重叠超过较矮一块的一半就算同一行，
行内从左到右排列并编号。抽取器和对齐器使用同一套行号。

**2. 模型同时回答行号（提示词 extract-v2）。** 每个字段输出 `{"value": ..., "row": ...}`，
行号只作为查找线索，不作为证据。

**3. 文字比对对齐器（`plugins/aligners/text_match.py`）。**

- 先查模型说的那一行，再查其他行。
- 数字、日期：生成原文可能的写法（9.00、1,234.50、25/12/2018……），用正则精确匹配，
  前后不能紧挨别的数字。不带小数的写法只在模型指定的行里使用，避免撞上数量、编号。
- 文字：忽略空格和大小写，用相似度比较（≥ 0.85）；可以跨连续 2～4 行（地址）。
- 状态：matched（一致）、fuzzy（相似）、not_found（找不到）、empty（模型说没有）。
- 需要人工确认：fuzzy、not_found、行号和模型说的不同、OCR 置信度低于 0.8。附带中文原因 `note`。
- 每个出处记录行号、行文字、文字块、合成的坐标框，用于审核页面高亮。

**4. 字段清单。** `receipt`（4 个常用字段）和 `full`（14 个单值字段），命令行用 `--fields` 选择。

## 局限

- 对齐只检查"值在不在原文里"，不检查"值对不对"。OCR 读错的原文（100）会被当作有出处，
  要靠规则校验（validators）发现。
- 不检查字段有没有选对，例如把人名当成商家名。改进提示词和字段说明，最后靠人工审核。
- 商品明细是表格，暂不抽取，等表格识别接入。
- 相似度、置信度的阈值是估计值，有评测数据后再调整。

## 第一次试用（SROIE 第 0 张收据）

`full` 清单 14 个字段：11 个找到出处（地址跨 4 行），2 个模型说没有，1 个标红（找零：
模型答 1.0，OCR 原文是 100）。抽取约 7.6 秒，比 4 个字段慢，主要因为要生成的内容更多。

## 后果

- 每个值都有出处或明确的"需要确认"原因，审核页面可以直接使用。
- 字段说明会影响结果（例如"通常在最上方"让模型选错商家），改字段说明也要谨慎，
  以后字段清单要有自己的版本号。
