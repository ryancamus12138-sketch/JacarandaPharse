# 0006 规则校验：用单据上的数字互相验证

- 状态：已采纳
- 日期：2026-11-03

## 背景

证据对齐只检查"值在不在原文里"。OCR 会高置信度地读错原文（找零 1.00 读成 100，置信度 1.00），
模型照抄后，对齐会认为它有出处。需要另一种不依赖 OCR 置信度的检查。

## 决策

**规则即数据。** 每条规则是 `Rule(id, title, needs, check, severity)`：
`check` 是一个函数，通过返回 None，不通过返回一句给人看的话。新增规则只需写函数并在清单里加一行。

**收据规则（`plugins/validators/rules.py` 的 RECEIPT_RULES）：**

| 规则 | 严重程度 |
| --- | --- |
| 总额大于 0 | error |
| 日期真实存在（JSON Schema 只管格式，管不了 2 月 30 日） | error |
| 日期不在未来 | warning |
| 小计 + 调整 = 总额 | error |
| 现金不少于总额 | error |
| 现金 − 总额 = 找零 | error |

**约定：**

- `needs` 里的字段有一个没值，规则就跳过，不算错，并在结果里列出。
- 金额比较用容差 0.005（浮点数有误差，0.1 + 0.2 ≠ 0.3）。
- 规则不知道是哪个值错了，所以把牵涉的字段全部标出；命令行里这些字段显示为黄色。
- 校验器只看字段值，不看 OCR，和对齐器互相独立。

## 第一次试用（SROIE 第 0 张收据）

- `full` 清单：6 条全部通过。找零被对齐器标红（模型答 1.0，OCR 原文是 100）。
- 模拟模型照抄 100：对齐通过，规则"现金 − 总额 = 找零"不通过，现金、总额、找零三个字段标黄。
- 两层检查从不同方向发现同一个 OCR 错误。

## 局限

- 只有收据规则。发票（税额、税率、明细合计）以后按同样方式增加规则清单。
- 金额汇总、导出时应改用 Decimal 精确计算。
- 规则判断不了是哪个值错了，仍需人工看图。

## 后果

- 流水线变成：OCR → 抽取 → 对齐 → 校验。对齐管"有没有出处"，校验管"互相对不对得上"。
- 规则清单以后可以和模板绑定，用户在网页上为不同单据选择不同规则。
