# 0014 人工审核

- 状态：已采纳
- 日期：2026-11-07

## 背景

流水线会把没把握的字段标成"需要确认"（对齐不上、规则不通过），但还没有办法修改或确认它们。
项目规则 2 要求模型原值永远保留，规则 3 要求审计记录只追加。审核功能要同时满足：
看得到当前值、查得到原值、查得到每一次是谁在什么时候改成了什么、为什么。

## 决策

**原值表不改，审核另存。** `extracted_values` 写入后不再更新（包括 `needs_review`）。
每次修改或确认都新增一条 `value_revisions`：

| 列 | 含义 |
| --- | --- |
| `seq` | 同一个字段的第几次审核，1、2、3…… |
| `action` | `edit`（修改）或 `confirm`（确认原来的值是对的） |
| `new_value` | 这次审核之后的值；确认时就是被确认的值 |
| `reason` | 原因；修改时必填 |
| `user_id`、`created_at` | 谁、什么时候（来自 OwnedMixin、TimestampMixin） |

**当前值是算出来的，不存。** `current_value` = 最新一条审核记录的 `new_value`，没有记录就是原值。
`reviewed` = 有审核记录；`pending_review` = 抽取时标了需要确认，并且还没有审核记录。
API 只新增这三个字段，原来的 `value`、`needs_review` 意思不变（项目规则 9）。

**并发：`(value_id, seq)` 唯一约束。** 两个人同时审核同一个字段，算出来的 seq 一样，数据库只接受一条，
另一个返回 409 "刚被别人审核过，请刷新"。不用加锁，也不会悄悄覆盖别人的修改。

**新值按类型检查并整理。** 数字去掉千分位、存成和原值一样的格式（`9.50` → `9.5`），拒绝 NaN、无穷大；
日期只接受 `YYYY-MM-DD`；空字符串和 null 表示"原文里确实没有"。新值和当前值一样时提示改用确认。

**所有字段都能审核，不只是标黄的。** OCR 和模型一起错时（例如 `.` 认成 `_`，模型照抄），
对齐和规则都发现不了，只能靠人。标黄只决定"必须看"，不限制"能改"。

**文档状态加一个 reviewed。** 所有需要确认的字段都处理过之后，调用 `POST /documents/{id}/review`，
done → reviewed；还有没处理的返回 409 并说明剩几个。已审核的文档再改字段，回到 done，需要重新完成审核。
只有 done 和 reviewed 的文档能审核字段（还在处理或处理失败时没有结果可审）。

**接口：** 审核记录是新增的资源，所以用 `POST /values/{id}/revisions`（201），而不是 PATCH 字段本身；
`GET /values/{id}/revisions` 返回原值和全部记录。

## 后果

- 导出 Excel 目前还是用模型原值；导出 API（以后）要改用 `current_value`。
- `evidence` 记录的是模型原值的出处，不随审核改变；审核页面把原图位置、OCR 文字、当前值放在一起看。
- 审核记录本身就是这部分的审计日志；登录、上传、删除等其他操作的审计日志在做账号功能时统一加。
- 查详情要多查一层 `revisions`（`selectinload`，一次查完，不会 N+1）；列表的待确认数用 `NOT EXISTS` 子查询。

## 放弃的方案

- **直接更新 `extracted_values.value`，另存旧值**：违反规则 2，而且"原值"和"当前值"的意思会随时间变化，难以追查。
- **在 `extracted_values` 上加 `current_value` 列**：要和审核记录保持一致，两处写入容易漏；算出来的值不会错。
- **用 `created_at` 排序**：同一事务或同一秒内的两条记录顺序不确定（SQLite 只精确到秒），所以加了 `seq`。
- **乐观锁要求前端传版本号**：更严格，但前端还没做；现在用唯一约束兜底，以后需要时可以加 `expected_seq`。
