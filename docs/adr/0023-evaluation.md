# 0023：评测方案——先在 SROIE 上量出基线

- 状态：已采纳
- 日期：2026-11-11

## 背景

v1 做完了，但不知道准不准：改提示词、换模型、加发票模板之后，没法判断是变好还是变差。
产品的核心承诺是"没标黄的值可以信"，这一点也需要数字来证明。

## 决定

1. **评测代码放在 `backend/src/jacara/eval/`**，用 `jacara eval` 命令运行。它只在开发时用，不属于产品运行时。
2. **第一个评测集用 SROIE**（英文收据，626 张，有标准答案）。评 3 个字段：商家、日期、总额；SROIE 没有单号。
   数据放在 `datasets/sroie/`，结果放在 `results/eval/<时间>/`，两者都不进 Git。下载命令 `jacara eval download` 要联网，只在开发机上用一次。
3. **评测走和产品完全一样的流水线**（`Pipeline.run`），标黄的判断也和审核页面一样（找出处的结果 + 规则校验）。
4. **比对前先统一格式**：数字按数值比；日期解析成年月日再比（SROIE 写法很多）；文字只比字母和数字，忽略大小写、空格和标点。
5. **六个指标**，每个字段一行，再加"全部"：
   - 准确率：模型的值对不对；
   - 出处覆盖率：原文里找到出处的比例；
   - 错值拦截率：错的值里被标黄的比例；
   - 误报率：对的值里被标黄的比例；
   - 放行率：没标黄、直接放行的比例；
   - **放行准确率**：直接放行的值有多准——"没标黄的就可以信"靠它证明，是最重要的一个。
   不找出处、直接用模型输出时，拦截率是 0，放行准确率等于准确率，所以不用单独跑对照组。
6. 每次重要改动（提示词、模型、对齐规则）后跑一次，把 `summary.md` 贴进 `docs/eval/README.md` 的记录表。
   暂不接入 CI：要跑本地大模型，CI 上跑不了；以后再考虑用固定的模型输出做回放测试。

## 没有选的方案

- **只算准确率**：看不出"找出处"的价值，也说明不了用户能不能信任没标黄的值。
- **另建一个 eval 包**：要多维护一套依赖；评测本来就要调用产品的流水线，放在同一个包里最简单。

## 影响

- `CLAUDE.md` 里"不要自行添加 eval/"的限制取消，改为本 ADR 的规则。
- 发票、检验单等新模板，要先准备评测数据，再接入同一套指标。
