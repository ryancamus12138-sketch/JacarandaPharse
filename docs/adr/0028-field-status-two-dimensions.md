# 0028：字段双维度状态（证据 × 校验）和"采用原文值"

- 状态：已采纳
- 日期：2026-11-12

## 背景

v1 每个字段只有一个"要不要人确认"（`needs_review`），标黄。审核员看不出为什么黄：
是原文里找不到这个值？只是 OCR 认错了一个字？还是值对上了原文、规则却不通过？
这三种情况要做的事不一样，优先级也不一样。设计说明第十一节 v2 第 4 项：
"字段双维度状态：证据（已验证 / 待确认 / 无证据）× 校验（通过 / 失败），按红、黄、绿分色排序"，
以及"采用原文值"。

## 决定

1. **证据**（`evidence_state`，`ExtractedValue` 上的属性，只看抽取时的出处，审核之后不变）：
   - `verified` 原文里找到、和值完全一致、没有疑点
   - `pending` 找到了，但只是相似、行号不对、OCR 置信度低或正负号不对（对齐器写了说明）
   - `missing` 原文里找不到
   - `empty` 模型说原文没有这个字段（人工新加的格子也是）
2. **校验**（`check_state`）：按**当前值**重新检查规则（ADR 0027 的 `current_checks`），
   字段牵涉在"错误"级规则里是 `fail`，"警告"级是 `warn`，否则 `ok`。
3. **颜色**（`level`，`pipeline/current.py` 的 `level_of`）：
   - 红：`fail`；或者 `missing` 且没人审核过
   - 黄：`warn`；或者 `pending` 且没人审核过
   - 灰：`empty` 且没人审核过；删掉的行
   - 绿：其他（原文一致，或者人确认、修改过）

   人确认过也照样按规则标色：值和原文对上了、规则却不通过，说明单据本身对不上，要让人知道。
   `check_state` 和 `level` 只在文档详情（`GET /documents/{id}`）里有，因为要整页一起算规则。
4. **排序**：审核页面右边可以"按状态"（默认）或"按单据顺序"，选择记在浏览器里。
   按状态时只排普通字段，商品明细的行不重新排；排序只看证据和校验、不看审核过没有，
   所以确认完一个字段它会变绿，但不会突然跳到最下面，↑↓ 走的时候位置不乱。
5. **原文值**（`source_value`）：按抽取时出处那几块文字得到的值，和当前值不一样时才有。
   - 文字字段：只是相似匹配时，原文那几块的文字（例如模型把 OCR 的 "TA _K" 改写成 "TAK"）。
   - 数字：原文里**同一个数**带负号（折扣 1.00-）而值是正的，或者反过来。
     不拿同一行别的数字顶替（"2 @ 3.00 6.00" 里单价 3.0 不会变成 6.0）。
   - 日期不给：25/03/18 是日/月/年还是月/日/年，单看原文判断不了。

   页面上点"采用原文值"，把原文的写法和原因填进表单，人看一眼再保存（原文那几块可能多带了别的字）。
   保存就是一次普通的修改，留审核记录。
6. **出处文字**：新抽取的出处多存一项 `text`（出处那几块的文字）；从原文选取、框选的出处也存。
   更新前处理的文档没有存，就用这一页的 OCR 结果（ADR 0027）取中心点落在出处框里的文字块，
   只在读的时候算，**不改**数据库里的出处（项目规则 2）。

## 后果

- 审核员先看红的、再看黄的；一眼看出是"证据"的问题还是"规则"的问题。
- "待确认"（`pending_review`）的意思不变，"全部确认""完成审核"照旧按它数。
- 文档列表、工作台按颜色筛选（v2 第 6 项）可以直接用这几个状态。
